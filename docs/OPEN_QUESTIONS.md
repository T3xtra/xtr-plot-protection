# Open Questions and Technical Investigations

The coding agent should keep this document up to date while working. A question may only be removed once the decision has been made explicitly or has been reliably resolved by a documented technical investigation.

## A. Product decisions, to be confirmed before release

### A1. Visualization of plot bounds
**Decided (2026-10-30):** purple dust particles along the edges of each plot box, sent only to players holding a Book and Quill (any, so new plots can be planned with a blank book). The plot of a held original book is green. Plots in setup show columns at their registered markers. Only the part within `boundsViewRange` is drawn, redrawn every `boundsViewIntervalTicks`. Addition: a ring at the viewer's foot height along the side faces, so a player far from every edge of a large plot still sees the wall. The questions below are answered by this.
It was announced that there is another idea for visualizing plot bounds. The concrete idea is not contained in the available notes. **Do not invent a visualization yourself.** Before implementing this feature, clarify:
- Who should see the bounds: owner, members, all players or only OPs?
- Should the display be temporary (e.g. on request) or permanent?
- Which type of display is meant?
- Should the vertical extent minY/maxY be visible?
- Which performance and visibility limits are acceptable?

### A2. Protection during marker repair
**Decided (2026-10-30):** the plot stays fully protected with its normal mode and door setting until the countdown expires. `REPAIR_PENDING` protects exactly like `ACTIVE`.

### A2b. Interactions in regenerative mode
**Decided (2026-10-30):** unauthorized players may open block inventories in `REGENERATIVE` plots to look inside, but cannot take items out (ender chests excepted). Other block state changes (repeaters, note blocks, placing, mining, …) are allowed and regenerated. Doors/trapdoors/fence gates follow the door setting. In `PROTECTED`, opening block inventories is denied.

### A3. Regeneration time model
**Decided (2026-10-30):** every changed block has its own clock. The delay starts with the block's first unauthorized change; the configured "duration" is a batch limit (maximum number of blocks restored per tick). A block changed again before its restoration keeps its original snapshot. Because entries are per block position, overlapping areas need no job merging: one entry per dimension + position.

### A4. Block entity and inventory snapshots
**Decided (2026-10-30):** all block entities are snapshotted with their full NBT (chests, barrels, furnaces, hoppers, shulker boxes, signs, …). Restoration overwrites the current content with the snapshot, so items put in or taken out during the delay are replaced by the snapshot state. Restoring a block and removing its entry happen in the same commit, so a restart either sees the entry (and restores again, overwriting — idempotent) or does not. If a block entity cannot be recreated, the entry is kept and logged instead of being dropped.

### A5. Owner transfer
Must the target owner already be a group member? Safe default in this specification: transfer only to an existing member, unless explicitly decided otherwise. **The safe default is implemented** (`PlotService.transferOwner`).

### A6. Admin and command permissions
**Decided (2026-10-30):** admin commands (replacement book for foreign groups, emergency owner transfer, settings of foreign plots) require OP level 3. For `/plot book <group>`, owner-only for normal players. Levels per command are listed in `COMMANDS.md`.

### A7. All four markers removed
**Decided (2026-10-30):** the general countdown rule applies; the plot stays protected until the countdown expires. The owner additionally gets the clickable delete option, deletion requires explicit confirmation, nothing is deleted automatically.

### A8. Plot creation
**Decided (2026-10-30):** every player (OP level 0) can create a plot in two ways:
- `/plot create <name>`: plot and group get `<name>`; the first original book is put into the inventory.
- Using an unregistered Book and Quill on an unregistered Lodestone: the first line of page 1 becomes plot and group name (empty → `<player>'s plot`), the book becomes the original and the Lodestone the first marker.

### A9. Changing mode, door setting, names and heights
**Decided (2026-10-30):** two paths:
- Commands (`/plot set …`), only for the owner or an OP (level 3).
- Editing page 1 of the original book. Page 1 is still generated by the system, but the setting lines (plot name, group name, mode, doors, minY, maxY) are parsed back. Valid values are applied, invalid or unparseable values are ignored and page 1 is regenerated from the data model. Display-only lines (owner, status, dimension, markers) are always regenerated. Like the member pages, this is not bound to the editor's identity.

### A10. Provisional defaults (please confirm)
The following values are implemented but not specified:
- Protection mode of new plots: `PROTECTED`, direct door opening: off.
- Repair countdown: 600 s (10 min), decided on 2026-10-31; changeable in game by OP level 3 via `/plot config`. Backup count: 20.
- Plot and group names: 1–32 characters, not unique (ambiguity is resolved via the group ID).
- Owner transfer: the previous owner remains a regular member.
- A plot before its first complete marker registration has the status `SETUP` (protects nothing). Marker removal in this status does not start a countdown.
- A plot with status `DISABLED` becomes `ACTIVE` again as soon as all four markers are re-registered with the original book. A replacement marker must have the same X/Z position as the missing one (Y may differ), because three corners already define the rectangle.
- Overlap is checked three-dimensionally (including minY/maxY): plots of different owners stacked on top of each other are allowed.
- `/plot delete` only works when the plot has no valid markers left (all removed, or never registered).
- Regeneration: delay 120 s, 20 blocks per tick, spread 60 s (blocks of one change reappear one after another, lowest first); delay and spread decided on 2026-10-31. Regeneration timers count game ticks (follow `/tick`, pause while offline). OP level 3 can change these in game via `/plot config`. Unauthorized fluid placement (buckets) in `REGENERATIVE` plots is refused rather than regenerated, because flowing fluids change blocks that were never snapshotted. Endermen never pick up blocks in `REGENERATIVE` plots (a regenerated carried block would be duplicated).
- Missing keys in the config file are filled with their defaults and written back (logged); unparseable files or invalid values still abort the start.
- Copies of an original Book and Quill that are bit-identical (creative mode, dupes) cannot be told apart from the original; see `ARCHITECTURE.md` known limits.

### A11. Translation review
**Decided (2026-10-30):** all seven languages stay. Non-English texts were written without native-speaker review; a review (especially Chinese and Japanese) is welcome but not a release blocker.

## B. Technical investigations

### B1. Server-side book editing
For the pinned Minecraft/Fabric version, demonstrate how Book and Quill changes are intercepted, validated and synchronized server-side. If the API offers no stable hook, document a technical alternative without circumventing the requirements.

**Resolved:** mixins on `ServerGamePacketListenerImpl.updateBookContents` and `signBook`, covered by GameTest `bookEditAppliesValidSettingsAndResetsInvalidOnes` (real edit packet).

### B2. Cause of explosions and fire
**Resolved:** explosions via the explosion's indirect source entity, fire is never attributable (see `ARCHITECTURE.md` known limits). Original question: Check how reliably the cause can be attributed to a player. An unclear cause must be handled safely according to the specification: regenerative handling for explosion/fire without an authorized initiator; creeper always regenerative.

### B3. Pistons, liquids and block updates
**Resolved:** mixins listed in `ARCHITECTURE.md` §6 with GameTests for pistons and liquids. Original question: Check the actually available Fabric hooks for all relevant mechanics. Merely checking the direct player mining event is not sufficient.

### B4. Entity transport
**Resolved:** leashing, riding, vehicle pick-up and fishing rods are covered; water currents/portals built by members and mobs following strangers are known limits. Original question: Test boats, minecarts, leads, water currents, portals and other relevant mechanics in the pinned version. Document which mechanics can be fully intercepted.

### B5. Config library and data format
**Resolved:** JSON via the Gson shipped with Minecraft, see `ARCHITECTURE.md` §6.

### B6. Marker removal vs. regeneration
**Resolved:** marker breaking is decided by `MarkerHandler` before any protection or regeneration rule (original book required, never regenerated); indirect changes never touch markers (GameTests). Original question: Legitimate marker removal with the associated original book must trigger the repair countdown and not be immediately undone by generic regeneration. Unwanted destruction by explosion/fire/mechanics must preserve or repair the marker. Prove event order and priority with an integration test.

## C. Release blockers

- No invented bounds visualization concept.
